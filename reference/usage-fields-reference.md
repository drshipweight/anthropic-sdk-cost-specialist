# Usage Fields Reference

Every cost recommendation maps back to fields on `response.usage`. Read these wrong and your dashboard lies to you. Below are the fields you will see, what each one counts, and how to multiply them against the prices in `pricing-snapshot.md`.

## The four token streams

Every Claude API response returns these four fields under `usage`:

| Field                          | Counts                                                           | Priced at        |
| ------------------------------ | ---------------------------------------------------------------- | ---------------- |
| `input_tokens`                 | Tokens **after** the last cache breakpoint, sent fresh           | Base input price |
| `cache_creation_input_tokens`  | Tokens written to the cache on this call                         | Cache write price (1.25× input for 5m, 2× input for 1h) |
| `cache_read_input_tokens`      | Tokens retrieved from cache on this call                         | Cache read price (0.1× input) |
| `output_tokens`                | Tokens generated by the model (includes any extended thinking tokens — see `extended-thinking-cost.md`) | Base output price |

**Total input rule:**

```
total_input_tokens = cache_read_input_tokens + cache_creation_input_tokens + input_tokens
```

If your dashboard tracks only `input_tokens`, it is under-reporting the input side of the bill.

## TTL breakdown (when using both 5m and 1h caches)

If you mix 5-minute and 1-hour breakpoints in the same request, `usage.cache_creation` breaks down the write further:

```json
"usage": {
  "input_tokens": 50,
  "cache_creation_input_tokens": 7345,
  "cache_read_input_tokens": 7123,
  "output_tokens": 503,
  "cache_creation": {
    "ephemeral_5m_input_tokens": 2345,
    "ephemeral_1h_input_tokens": 5000
  }
}
```

The two `cache_creation.ephemeral_*` fields sum to `cache_creation_input_tokens`. Use them when you need to attribute write cost to the right TTL.

## Server-tool fields (only if you use server tools)

Server-side tools like web search and code execution add their own fields under `usage.server_tool_use`:

```json
"usage": {
  "input_tokens": 105,
  "output_tokens": 6039,
  "cache_read_input_tokens": 7123,
  "cache_creation_input_tokens": 7345,
  "server_tool_use": {
    "web_search_requests": 1
  }
}
```

Web search bills $10 per 1,000 searches separately from token cost. Web fetch and code execution have their own pricing (see `pricing-snapshot.md` link). For the full tool-cost surface — definitions as input tokens, caching the `tools` block, and how chains compound across turns — see `tool-use-cost.md`.

## Cost calculator (TypeScript, paste-ready)

Drop this into any project. Uses the prices from `pricing-snapshot.md`. Verify against the live page before using for billing.

```ts
type Usage = {
  input_tokens: number;
  output_tokens: number;
  cache_creation_input_tokens?: number;
  cache_read_input_tokens?: number;
  cache_creation?: {
    ephemeral_5m_input_tokens?: number;
    ephemeral_1h_input_tokens?: number;
  };
};

type Prices = {
  input: number;        // $/MTok
  output: number;       // $/MTok
  cacheWrite5m: number; // $/MTok
  cacheWrite1h: number; // $/MTok
  cacheRead: number;    // $/MTok
};

const PRICES: Record<string, Prices> = {
  "claude-opus-4-7":   { input: 5, output: 25, cacheWrite5m: 6.25, cacheWrite1h: 10, cacheRead: 0.5 },
  "claude-sonnet-4-6": { input: 3, output: 15, cacheWrite5m: 3.75, cacheWrite1h: 6,  cacheRead: 0.3 },
  "claude-haiku-4-5":  { input: 1, output: 5,  cacheWrite5m: 1.25, cacheWrite1h: 2,  cacheRead: 0.1 },
};

export function estimateCallCost(model: string, usage: Usage): number {
  const p = PRICES[model];
  if (!p) throw new Error(`Unknown model: ${model}`);

  const write5m = usage.cache_creation?.ephemeral_5m_input_tokens ?? 0;
  const write1h = usage.cache_creation?.ephemeral_1h_input_tokens ?? 0;
  const writeOther =
    (usage.cache_creation_input_tokens ?? 0) - write5m - write1h;

  const totalWriteAt5m = write5m + Math.max(writeOther, 0);

  return (
    (usage.input_tokens * p.input +
      usage.output_tokens * p.output +
      totalWriteAt5m * p.cacheWrite5m +
      write1h * p.cacheWrite1h +
      (usage.cache_read_input_tokens ?? 0) * p.cacheRead) /
    1_000_000
  );
}
```

A few notes on this helper:
- It assumes anything in `cache_creation_input_tokens` not attributed to `ephemeral_1h_input_tokens` is at the 5-minute rate. That is a safe default; if you mix TTLs, always read the breakdown.
- It returns the **standard-tier, global-routing, non-fast-mode** cost. Apply these multipliers on top of the result if applicable (verify on the live pricing page; multipliers change):
  - **Batch API**: × 0.5 across input, output, cache write, and cache read.
  - **US-only data residency** (`inference_geo: "us"` on Opus 4.6 and newer): × 1.1 across all token categories.
  - **Fast mode** (currently Opus 4.6 only): × 6 on input and output ($30 / $150 per MTok). Stacks with the data-residency multiplier; mutually exclusive with Batch API.
  - **Priority Tier**: separate per-model multiplier — see `priority-tier-cost.md`.
- Track the per-call cost alongside latency and cache-hit rate. The three numbers together tell you whether your caching is paying off.

## What "good" looks like

Healthy traffic on a properly cached prompt has:

- `cache_read_input_tokens` ≫ `cache_creation_input_tokens` (most calls hit cache)
- `input_tokens` small relative to total input (most input is cached)
- A non-zero `cache_creation_input_tokens` only on the first call within each TTL window, or after the cache prefix changes

If `cache_creation_input_tokens` is non-zero on most calls, your cache key is changing on every request — usually because volatile content sits before a cache breakpoint.

> **Verify against:** [platform.claude.com/docs/en/build-with-claude/prompt-caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
